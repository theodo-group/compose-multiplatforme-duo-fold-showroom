Kotlin 2.4.21 · Compose Multiplatform 1.12.2 · material3-adaptive 1.3.0

Une seule UI pour deux pliables

Fold Showroom est un catalogue de 13 démos Compose Multiplatform pour l'iPhone Duo et le Pixel 9 Pro Fold. Cette page explique comment l'app est construite : les composants, les APIs internes, et les patterns qui permettent de garder 74 % du code dans commonMain.

4 347 lignes partagées (74 %) 532 lignes Android (9 %) 958 lignes iOS (16 %)

Ce que l'app cherche à prouver

  • Tout ce qui dépend de la taille de la fenêtre s'écrit une fois, en commun : 7 démos sur 13 n'ont aucune ligne native.
  • Ce qui dépend du pli physique demande une petite source native, écrite une seule fois et exposée par ProvideFoldState.
  • Ce qui dépend d'une API propre à un OS (écran extérieur, multi-fenêtre) demande du vrai code natif, isolé derrière une interface commune.

Organisation des sources

  • core/ : le squelette de l'app (catalogue, hôte des démos, barres, thème, retour).
  • fold/ : le modèle FoldState et sa source par plateforme.
  • demos/{layout, panes, hinge, platform}/ : une démo par fichier.
  • nativeInterop/cinterop/ : deux ponts Objective-C pour les API iOS 27.1.
  • iosApp/ : l'hôte SwiftUI et l'accessoire d'écran extérieur.
01 · Points d'entrée

Du lancement natif à App()

Chaque plateforme fait le minimum : créer une surface Compose et appeler App(). Il n'y a ni ViewModel, ni navigation native, ni injection de dépendances. Toute la logique commence dans le code commun.

Android

androidApp/…/MainActivity.kt

enableEdgeToEdge() est appelé avant super.onCreate : Compose gère lui-même les insets. Le manifeste déclare configChanges, si bien que l'activité n'est pas recréée au pli, au dépli ni à la rotation.

iOS

iosApp/iOSApp.swift → ContentView.swift → MainViewController.kt

Swift enregistre d'abord le pont d'écran extérieur (OuterDisplayModel.shared.register()), puis chaque scène affiche un ComposeUIViewController qui exécute son propre App().

03 · fold/FoldState.kt

ProvideFoldState

Une seule source de vérité pour la charnière, lue partout via LocalFoldState.current.

material3-adaptive lit la posture depuis Jetpack WindowManager. Sur Android, c'est correct. Sur iOS, cette posture reste toujours « à plat » : la bibliothèque ne voit pas la charnière de l'iPhone Duo. Le projet définit donc son propre modèle FoldState, neutre vis-à-vis de la plateforme, et une source expect/actual pour le remplir.

Le modèle

Il n'y a pas de champ « occultant ». Une charnière occultante se traduit par un hingeBounds d'épaisseur non nulle et isSeparating = true. Sur l'iPhone Duo et le Pixel Fold, le pli est sans couture : l'épaisseur est souvent nulle.

Le provider

  • compositionLocalOf dynamique : seuls les composables qui lisent la valeur se recomposent quand la charnière bouge.
  • Valeur par défaut FoldState.None (null object) : un composable prévisualisé ou testé hors de App() fonctionne sans pliure.
  • Appelé une seule fois, dans App.kt:20. Les démos lisent le local, jamais rememberPlatformFoldState() directement.

Deux sources, un contrat

Jetpack WindowManager fournit la FoldingFeature (position, orientation, état). Un capteur TYPE_HINGE_ANGLE (API 30+) fournit l'angle.

  • La collecte est liée à la composition (LaunchedEffect, DisposableEffect), pas au Lifecycle.
  • foldStateOf() traduit les types Android vers le modèle commun : HALF_OPENED + vertical donne Book, HALF_OPENED horizontal donne Tabletop.
  • Sans FoldingFeature mais avec le capteur (pliable utilisé sur son écran externe), hasHinge = true et la posture vaut Closed sous 30°.

Une UIView invisible, SHHingeObserverView, est insérée au fond de la vue hôte Compose. Son callback écrit directement dans un MutableState, ce qui recompose les lecteurs.

  • toFoldState(density) convertit les points UIKit en pixels Compose et les radians en degrés.
  • hingeStatus 2 (entrouvert) donne Tabletop si le pli est horizontal, Book sinon.
  • onDispose appelle detach(), qui casse le cycle de références entre Kotlin et Objective-C.

Les bindings Kotlin/Native 2.4.21 sont générés depuis le SDK iOS 26.4 : UIHingeInteraction (iOS 27.1) n'y existe pas. Le pont l'atteint par le runtime Objective-C.

  • Classes résolues par NSClassFromString, chaque appel protégé par respondsToSelector:. Le code compile avec un SDK ancien et reste inerte sur un système ancien.
  • La région « division » peut arriver après la charnière : le pont relit jusqu'à 10 fois toutes les 100 ms, avec un compteur de génération contre les courses.
  • Le .m est inclus après --- dans hinge.def, car l'indexeur cinterop refuse un @implementation dans le fichier de définition.
  • Adapté de Crease (MIT), voir THIRD_PARTY_NOTICES.md.
Re-fournir le local pour simuler. L'écran « Jauge de charnière » lit l'état réel, lui applique des réglages (charnière occultante, angle) avec withTweaks(), puis re-fournit LocalFoldState à son seul sous-arbre. FoldAwareTwoPane et tout le contenu de l'écran voient l'état simulé ; le reste de l'app garde l'état réel.

04 · core/BarPlacement.kt

ProvideBarPlacement

Où dessiner Back, les actions et les onglets : en haut, ou dans une barre verticale sur le côté.

Les deux plateformes n'ont pas la même règle. Material 3 garde Back et les actions dans la top app bar à toutes les tailles ; seules les destinations de premier niveau passent dans un rail. Les guidelines iPhone Duo placent Back, les actions et les onglets dans une barre verticale, du côté de la barre système, sur l'écran externe et sur l'écran interne en paysage. ProvideBarPlacement expose cette décision à toute l'UI, pour qu'aucun écran n'ait à la refaire.

Le type et le provider

Les deux actuals

Sur iOS, SHVerticalBarObserverView lit le trait UITraitCollection.verticalBarEdge (iOS 27.1) et s'abonne à ses changements. Il convertit leading/trailing en bord physique selon le sens d'écriture, et calcule itemsTop pour démarrer les contrôles sous la barre d'état verticale.

05 · core/CatalogScreen.kt · core/DemoScreen.kt

Pourquoi un CatalogScreen et un DemoScreen

Le catalogue choisit une démo. L'hôte l'habille. La démo ne fait que remplir l'espace.

Une démo est une simple valeur Demo dont le champ content est un slot composable. Tout ce qui est commun aux 13 démos (titre, badge, Back, bouton ⓘ, consommation des insets, gestion du retour, barre adaptative) vit une seule fois dans DemoScreen. Sans cette séparation, chaque démo devrait réimplémenter son chrome, et la moindre règle de barre iPhone Duo serait à corriger 13 fois.

CatalogScreen l'écran racine

  • Signature : CatalogScreen(demos, gridState, onOpen). Aucun état propre.
  • LazyVerticalGrid(GridCells.Adaptive(280.dp)), groupée par niveau Sharing, avec un en-tête pleine largeur par groupe.
  • Le sous-titre liveWindowSummary() (« 673 × 841 dp · posture à plat ») prouve que l'UI commune voit la vraie fenêtre et la vraie pliure.
  • Pas de Back, pas d'actions : c'est la racine.

DemoScreen l'hôte générique

  • Signature : DemoScreen(demo, onBack).
  • Titre + SharingBadge, Back, bouton ⓘ qui ouvre un ModalBottomSheet avec demo.notes.
  • Crée un BarItemsRegistry par démo (remember(demo.id)) et l'expose par LocalBarItems.
  • Applique padding puis consumeWindowInsets : la démo reçoit un espace déjà débarrassé des barres.
  • Enregistre le NavigationBackHandler qui ramène au catalogue.

Navigation par état, sans back stack

L'app n'a que deux niveaux. Un seul String? suffit : null affiche le catalogue, un identifiant affiche la démo correspondante. Il est en rememberSaveable, donc il survit à la rotation et à une recréation d'activité. Un identifiant inconnu ramène au catalogue.

catalogGridState est remonté au-dessus du if : quand on revient d'une démo, la grille retrouve sa position de défilement. Navigation 3 n'est utilisée que dans la démo qui la présente, pas pour l'app elle-même.

06 · core/AdaptiveBarScaffold.kt · core/BarItems.kt

AdaptiveBarScaffold et HostBarItems

AdaptiveBarScaffold a la même forme qu'un Scaffold Material (des slots title, navigationIcon, actions, content), plus une liste tabs. Il lit LocalBarPlacement et choisit son rendu dans un when exhaustif sur le type scellé.

En mode Side

  • Un NavigationRail du côté de placement.edge, d'au moins 64 dp, avec Back puis les actions en tête et les onglets en dessous.
  • Le rail démarre à max(top, itemsTop), sous la barre d'état verticale.
  • Le rail est dessiné même vide : la bande est réservée par le système.
  • Le titre devient un en-tête compact en haut du contenu.
  • En mode Top, les tabs sont ignorés : l'écran dessine sa propre barre d'onglets.

Faire remonter des boutons de la démo vers l'hôte

Une démo veut parfois mettre ses propres boutons dans la barre de l'hôte (onglets de la navigation adaptative, pages du mode livre). Or c'est l'hôte qui dessine la barre. HostBarItems inverse le flux : la démo déclare ses items, l'hôte les lit dans un registre.

  • SideEffect écrit les items à chaque composition réussie : le dernier appel gagne.
  • DisposableEffect les retire quand l'appel quitte la composition.
  • Un jeton propriétaire (remember { Any() }) garantit qu'un appelant n'efface que ce qu'il a posé.
  • Hors d'un DemoScreen, LocalBarItems vaut null et l'appel ne fait rien.
07 · core/SystemBack.kt

Le retour arrière, un seul dispatcher

Il y a trois façons de revenir en arrière : le bouton Back à l'écran, le retour système Android (y compris prédictif) et le geste de bord iOS. Elles passent toutes par le même NavigationEventDispatcher de androidx.navigationevent. Le handler le plus interne passe en premier : dans la démo Liste / détail, Back ferme d'abord le détail, et seulement ensuite la démo.

rememberSystemBack() fabrique un callback pour le bouton à l'écran. Au lieu d'appeler directement onBack, il injecte un événement dans le dispatcher via une DirectNavigationEventInput. Le commit 130f546 a remplacé le BackHandler déprécié par NavigationBackHandler, et corrigé un bug où le retour quittait la démo Navigation 3 au lieu de dépiler une entrée.

FoldAwareTwoPane

Le composant central des démos « charnière ». Il lit LocalFoldState, mesure sa propre position dans la fenêtre, convertit le pli dans son repère local (hingeIn()), puis choisit un TwoPaneMode et une TwoPaneReason qui explique ce choix. Rien n'est placé sous le pli.

    09 · demos/platform · iosApp

    Code natif : trois manières de l'isoler

    Le code natif ne remonte jamais dans l'UI. Selon la taille du besoin, le projet utilise l'une de ces trois techniques.

    expect/actual fin

    Quand seule une donnée change. Le glisser-déposer garde ses modificateurs Compose communs et ne délègue que la charge utile : ≈ 35 lignes Android (ClipData), ≈ 70 lignes iOS (NSItemProvider), aucune ligne Swift.

    Interface CapabilityController

    Quand le comportement entier change. PlatformKit définit un contrat commun et des composables de présentation. Chaque plateforme fournit un contrôleur adossé à de l'état Compose. L'UI ne connaît que l'interface.

    Pont Swift → Kotlin pour l'écran extérieur iOS

    CameraCaptureAccessory n'existe qu'en Swift et n'est pas dans les bindings Kotlin. Le projet inverse la dépendance : Kotlin déclare une interface, Swift l'implémente et s'enregistre au démarrage.

    Si aucun hôte n'est enregistré, la capacité s'affiche « non prise en charge » avec la raison. Le contenu de l'écran extérieur est le même composable OuterDisplayContent que sur Android.
